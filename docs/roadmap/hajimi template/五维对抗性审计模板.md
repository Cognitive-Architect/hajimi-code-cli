# 五维对抗性审计模板（v2.0 — SRC源码深度审查）

> **模板定位**: 长期可复用的红队审计框架，覆盖编码安全、可维护性、可用性、数据诚实、文档一致五大维度
> **适用场景**: 任何分层架构项目的源码交付前审查、债务清偿后验证、阶段性质量门禁
> **核心原则**: "找到就炸，没后果就标记误报，有后果就拉清单"

---

## 【饱和攻击头部】

**火力配置**: 3 Agent并行（红队安全审计员 ×1 / 代码考古学家 ×1 / 用户体验破坏者 ×1）

**五维覆盖**:
- **D1 编码安全性**: 漏洞、后门、供应链投毒、密钥泄露
- **D2 可维护性**: 史山代码、架构违规、认知负担

#### D1 收卷红线（Codex Security 升级版）

1. **发现可远程利用的 RCE 漏洞**（PoC 已验证）→ **最高后果**（立即熔断发布）
2. **发现硬编码生产密钥**（已验证落盘）→ 高后果（密钥轮换）
3. **发现高危发现但无 PoC/验证证据** → 审计失效（标记为"未验证猜测"）
4. **发现漏洞但未提供回归测试** → 审计不完整（无法验证修复有效性）
5. **扫描计划遗漏 P0 优先级模块**（shell/file/Tauri）→ 覆盖不全
6. **未区分"静态确认"vs"已验证"** → 结论不可信
7. **隐瞒依赖扫描结果**（声称"无漏洞"实际未运行 audit）→ 审计欺诈
8. **未评估后果**（仅列出漏洞未说明可利用性）→ 对抗性审计失效

## 【模块5】红队审计铁律（对抗性 + Codex Security 增强）

1. **后果强制**: 每处发现必须回答"So What?"——会导致什么实际损失？无后果则标记**误报**。
2. **可利用性优先**: 不报告仅理论存在但无可行攻击路径的漏洞。
3. **建设性破坏**: 找出问题后必须提供"最小修复成本"方案（非重构）。
4. **独立验证**: 所有结论必须有命令输出支撑，不接受"我觉得/应该"。
5. **无审计影子**: 用"风险评级：高/中/低/无后果"，不出现Audit/D级等词汇。
6. **四件套验证**（Codex Security）: 每个高危发现必须包含（攻击路径、代码证据、验证证据、修复建议），缺一不可。
7. **优先级分层**（Codex Security）: P0（shell/file/Tauri）> P1（API Key/MCP/Git）> P2（扫描器/CSP），资源优先聚焦P0。
8. **回归测试强制**（Codex Security）: 每个安全修复必须提供可复现的回归测试，禁止"修复了但无法验证"。
