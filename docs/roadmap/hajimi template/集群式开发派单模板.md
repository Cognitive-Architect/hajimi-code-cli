# ID-59 v3.0 通用增强版集群式开发派单模板

> **定位**: 单一通用模板，覆盖功能开发 / Bug 修复 / 重构 / 探索性任务
> **核心目标**: 保留原模板的高约束、高透明、高验证优势，同时移除容易诱导 AI 为凑形式而扭曲实现的设计
> **适用原则**: 不再为任务类型切换模板；统一用这一份模板派单，仅通过字段内容适配不同任务
> **核心方法**: 用**自动化质量闸门 + 结构化证据 + 债务透明化**替代**绝对行数限制**

---

## 【模块1】饱和攻击头部（通用增强版）

- **火力配置**：N Agent（仅 `Engineer` / `Architect`，无 `Audit` 角色）
- **任务名称**：[任务名称]
- **轰炸目标**：[精确到模块 / 文件 / 函数 / 工作流的一句话目标]
- **任务性质**：[功能开发 / Bug修复 / 重构优化 / 探索调研 / 混合任务]
- **输入基线**：完整技术背景表格（禁止仅写“参考ID-xxx”“见记忆YYY”“见上文”）
- **输出要求**：可执行产出 + 可复现验证 + 显式债务声明 + 结构化收卷
- **通用铁律**：
  1. **数据诚实**：所有数字、测试数、覆盖率、性能值、warning 数必须来自真实命令输出
  2. **零占位符**：禁止只给抽象结论，不给代码位置 / 命令 / 证据
  3. **自动化优先**：能用命令验证的，不靠主观口头说明
  4. **最小必要复杂度**：不为凑形式拆函数、堆注释、造中间层
  5. **债务透明化**：做不到的项必须显式声明，不得伪装为“已完成”

## 【模块2】输入基线（完整技术背景，零占位符）

> **规则**：即使是探索型任务，也必须把“已知”和“未知”分开写清，而不是直接省略。

| 输入项 | 强制要求 | 验证命令 / 证据方式 | 状态 |
|---|---|---|---|
| Git坐标 | 当前分支 + HEAD SHA | `git branch --show-current` / `git rev-parse HEAD` | 必须 |
| 目标范围 | 模块/文件/函数/工作流范围 | 路径列表 + 行号范围 + 当前行为摘要 | 必须 |
| 现状基线 | 当前实现、当前缺陷或当前缺口 | `sed -n 'X,Yp' file` / 现象复现命令 / 截图路径 | 必须 |
| 目标结果 | 交付后应达到的结果 | 文字描述 + 验收命令 | 必须 |
| 技术约束 | 架构、安全、依赖、风格、接口约束 | 文字展开，禁止“参考某记忆” | 必须 |
| 风险边界 | 禁止改动范围 / 高风险区域 / 不在本轮范围内项 | 路径或模块说明 | 必须 |
| 测试基线 | 当前编译 / 测试 / lint / fmt 状态 | 实际命令输出摘要 | 必须 |
| 文档同步要求 | 哪些文档需要同步更新 | 路径列表 | 按需 |
| 历史债务 / 相关缺陷 | 与本轮相关的既有 debt / 回归点 | 文档路径 / issue / 缺陷编号 | 按需 |

### 输入基线填写规范

1. **代码文件必须落到路径与行号范围**，不能只写“memory模块”“tool模块”。
2. **技术约束必须完整展开**，不能只写“按原有架构”。
3. **若任务具有探索性**，必须补充下表，而不是切换到另一份模板。

### 探索补充栏（仍然是同一模板的一部分）

| 项目 | 内容 |
|---|---|
| 已知事实 | [当前已确认的代码事实 / 接口事实 / 约束事实] |
| 待确认问题 | [尚未确认的关键问题，最多 3-5 条] |
| 预期输出 | [需要收敛出的方案 / 结论 / 修改点] |
| 停止条件 | [探索到什么程度即可进入实现 / 收卷] |

## 【模块3】工单矩阵（通用高压版）

> **说明**：此模板仍保留原版的“高约束并行工单”优势，但取消绝对行数限制，改为**质量闸门 + 复杂度观察 + 必要性证明**。

### 每个 Agent 必填字段

#### 1）基础信息
- **工单编号**：B-XX/XX
- **角色**：`Architect` / `Engineer`
- **目标**：一句话技术目标
- **输入**：引用输入基线中的具体项（必须能回溯到路径/命令/事实）
- **依赖关系**：是否依赖其他工单先完成

#### 2）输出交付物
- **变更文件**：[明确路径列表]
- **核心修改点**：[函数 / 类型 / 接口 / 流程]
- **必须包含**：[正则 / 结构 / 测试 / 文档 / 行为]
- **禁止包含**：[黑名单内容，如 mock 成功返回、硬编码结果、临时占位逻辑等]
- **交付证明**：[必须提供哪些命令输出 / diff / 自测结果]

#### 3）规模与复杂度观察（替代绝对行数限制）

> **不是硬性行数红线，而是结构化约束。**

- **推荐目标**：
  - 单函数保持单一职责
  - 单函数如明显过长（如 >50 行）需解释理由
  - 复杂分支 / 状态机 / 算法集中处，如超出常规复杂度，需声明 `DEBT-COMPLEXITY`
- **禁止行为**：
  - 为压行数 / 凑行数而硬拆函数
  - 为通过模板而添加无意义中间层
  - 用注释灌水代替真实设计说明
  - 用“先 fake 再补”伪装完成度

#### 4）自动化质量闸门（强制）

| 闸门 | 要求 | 验证命令（择适用栈填写） | 不通过后果 |
|---|---|---|---|
| BUILD | 编译 / 构建通过 | 例如 `cargo check --workspace` / `npx tsc --noEmit` / `python -m py_compile ...` | 返工 |
| FMT | 格式检查通过 | 例如 `cargo fmt -- --check` / `prettier --check` / `ruff format --check` | 返工 |
| LINT | 不新增 warning / error；如存在需声明 | 例如 `cargo clippy -- -D warnings` / `eslint .` / `ruff check` | 返工或声明债务 |
| TEST | 本轮变更具备对应测试或可验证证据 | 例如 `cargo test ...` / `npm test` / `pytest -q` | 返工 |
| ARCH | 不违反架构 / 分层 / 接口约束 | 约束检查命令或静态证据 | 返工 |
| REAL | 禁止假实现 / 假数据 / 假成功 | diff + 行为验证 + 自测证据 | 返工 |
| DOC | 该更新的文档必须同步 | 文档路径 + diff 证据 | 返工或声明债务 |

> **规则**：
> - 没有验证命令的检查点，不算有效检查点。
> - 仓库没有对应工具时，必须写 `N/A + 原因 + 替代证据`，不能空着。
> - “已验证”必须附实际输出摘要，不能只打勾。

## 【模块3-B】地狱红线（10项）

1. **零占位符违规**：出现“参考ID-xxx”“见记忆YYY”“见上文即可”等偷懒输入 → 返工
2. **验证造假**：声称已验证，但无法提供命令 / 输出 / 证据 → 返工
3. **编译 / 构建失败**：仍然声称“完成” → 返工
4. **测试缺失却伪装完成**：核心功能/关键负面路径无验证却交付 → 返工
5. **假实现**：mock 成功、硬编码成功、setTimeout 模拟、伪流式、伪 RPC → 返工
6. **架构 / 安全约束违反**：分层违规、接口契约破坏、越权改动 → 返工
7. **新增 warning / debt 不申报**：质量退化但未透明声明 → 返工
8. **范围失控**：擅自扩大修改范围，未说明影响与理由 → 返工
9. **Git 历史不完整**：擅自覆盖、抹平、删除用户已有工作痕迹 → 返工
10. **探索任务伪装确定性完成**：关键未知仍未澄清，却声称方案已闭环 → 返工

## 【模块6】技术熔断预案（非时间熔断）

> **保留原模板“熔断”优点，但从行数熔断改为技术熔断。**

| 熔断ID | 触发条件 | 动作 | 后果 |
|---|---|---|---|
| ARCH-001 | 发现既定契约在当前结构下无法成立 | 暂停实现，先收敛方案 | 返工或拆分工单 |
| QUALITY-001 | 自动化闸门无法通过且非一次性小问题 | 停止继续堆代码，先修质量问题 | 返工 |
| COMPLEXITY-001 | 连续 2 次返工后仍出现复杂度过高 / 结构过重 | 允许带 `DEBT-COMPLEXITY` 交付，但必须解释必要性 | 记录债务 |
| TEST-001 | 测试基础设施缺失，无法对关键路径做自动化验证 | 必须降级为可复现实测 + `DEBT-TEST` | 有条件交付 |
| PERF-001 | 性能明显回退或资源占用异常 | 停止扩展功能，优先处理回退 | 返工 |

### 复杂度熔断条款（替代 Flex-Line-Clause）

- **初始标准**：优先保持单函数单职责、无明显结构膨胀、自动化闸门全部通过
- **触发条件**：连续 2 次返工后，仍因必要复杂度无法满足“简洁实现”目标
- **熔断后要求**：允许保留较复杂实现，但必须：
  1. 显式声明 `DEBT-COMPLEXITY-[工单ID]`
  2. 说明复杂度来源（算法必要 / 状态机必要 / 接口约束 / 兼容性负担）
  3. 说明未来清偿计划（Phase X / 后续重构点）
- **禁止行为**：
  - 首次提交就预设“复杂度不可避免”
  - 不解释复杂度来源
  - 用“模板允许熔断”当作放弃设计的借口

## 【关键使用规范】

### 1. 单模板原则
- 不再按“探索级 / 标准级 / 地狱级”切换模板
- 始终用这一份模板
- 差异只体现在：输入基线是否包含“探索补充栏”、刀刃表具体命令、质量闸门命令选择

### 2. 质量优先于形式
- 不再使用绝对行数限制
- 改为：**自动化质量闸门 + 复杂度说明 + 必要性证明 + 债务透明化**

### 3. 命令优先于口头结论
- “已完成”“已验证”“无问题”都不算证据
- 必须有命令、输出摘要或可复现证据

### 4. 探索任务也必须结构化
- 探索不等于散漫
- 不能因为存在未知，就省略输入基线、验证方式、停止条件

### 5. 债务必须分类申报
- 推荐债务前缀：
  - `DEBT-COMPLEXITY-XXX`
  - `DEBT-TEST-XXX`
  - `DEBT-DOC-XXX`
  - `DEBT-SCOPE-XXX`
